Five-Minute Quick Start

From open browser to passing test in five steps

  1. Open the portal Sign in (or just open the demo URL during the preview phase). The home page lists what the platform can do; the navbar at the top is how you get around.
  2. Create a project Click Projects → New Project. Give it a name (e.g. Acme Sandbox) and a one-line description. This is the folder all your test work for that engagement lives in.
  3. Add your sandbox credentials Inside the project, open Settings for the project and add the sandbox URL, username, and password under the Dev environment, persona System Admin. You can add more environments and personas later.
  4. Generate a script Go to Generate, pick the project, type a prompt — e.g. "Create a Lead with first name Alex, last name Wong, company Acme, state CA". Hit Quick Generate. A complete .robot file appears.
  5. Run it Click Run on the generated script. Choose Headless (faster) or visible mode. The live log streams in. When it finishes, jump to the Run Dashboard for a clean summary.

Five minutes is realistic. The longest part is typing a credible prompt — the AI does the rest. Most testers have their first green Robot run in under ten minutes from a cold start.

Creating a Script from a Prompt

The bread and butter of the platform

The Generate page is the main place you'll spend your time. You give it three things — a project, a prompt, and a generation mode — and it gives you a complete Robot Framework script.

Step-by-step

  1. Pick a project. Determines which sandbox the script will target and which credentials get used.
  2. Pick an environment + persona. Defaults to Dev / System Admin. Switch to QA, UAT, or a different persona if needed.
  3. Write the prompt. Plain English. Mention object names, field values, and the action you want. Examples:
    • "Create an Account named Globex with billing state Texas. Verify it shows up in the recent items list."
    • "Open the existing Lead 'Sara Patel', change the company to Acme Corp, save, and check that the audit trail records the change."
    • "Convert the Lead 'Mike Rivera' to an Opportunity with stage Qualification."
  4. Choose the generation mode — see the two cards below.
  5. Review the script. The Robot file appears in a code panel. You can edit it inline before saving.
  6. Save it to your project. Give it a test name (e.g. create_account_globex). It lands under Tests/ in the project folder, ready to run.
🧞

Quick Generate

One LLM call — fast (5-10 s) for simple to moderate scripts. Best when you know roughly what the test should look like and want to iterate quickly.

🔌

MCP Stepwise

Each action is validated step by step against the live keyword catalog. Slower (30-90 s) but produces the most reliable scripts for unfamiliar flows.

Tip: Start with Quick Generate. If the script doesn't run cleanly the first time, regenerate using MCP Stepwise — it will catch invalid keywords and missing args before they become runtime errors.

Projects — Your Test Workspaces

Everything for one engagement lives in one project

A project is a folder. It groups everything you'd want to keep together: which sandbox to run against, who to log in as, which scripts you've saved, and which CSV data files those scripts use. You typically have one project per client, sandbox cluster, or release.

What lives inside a project

Project name
Used everywhere as the workspace label (e.g. Acme_Sandbox).
Description
Free text — what's this project for, who owns it.
Environments
Dev, QA, UAT, Prod — or whatever you name. Each environment can hold its own sandbox URL.
Personas
Per environment: System Admin, Marketing User, Read-Only Auditor, etc. Each persona stores its own username + password (encrypted at rest).
Tests
The .robot scripts you've generated and saved.
Data
CSV files for data-driven tests. Auto-injected as Robot variables when present.
Project settings
Optional Jira/Zephyr settings for future integration with defect tracking.

Common things you'll do here

  • Create a project — new client, new sandbox refresh, or to separate experiments from production work.
  • Add a new environment — e.g. when QA hands off to UAT; same project, different URL.
  • Add a new persona — same environment, different role (Marketing User in addition to System Admin).
  • Edit credentials — after a sandbox refresh or password rotation. The new password is encrypted and stored locally; nothing is exposed in generated scripts.
  • Delete a project — archives the entire folder. Tests, scripts, and credentials all go.
Heads-up on credentials: Passwords are encrypted with a project-wide key (FERNET_KEY) before they touch disk. They never appear in generated .robot files — the script reads them at run time from secure variables.

User Stories → Test Cases

Plan a sprint's coverage from acceptance criteria

The Stories tab is for when you want test design driven by what the product actually has to do, not by what someone happened to think of writing. Capture the acceptance criteria once, let the AI propose a full test matrix, and approve the cases you'd actually run.

The flow

  1. Create a story. Title plus a short description that includes the acceptance criteria. Example: "As a Marketing user, I can convert a Lead to an Opportunity. AC: stage defaults to Qualification; the existing Account is reused if the company name matches; an audit entry is written."
  2. Generate test cases. The AI reads the story and proposes 4-12 candidate test cases — happy path, edge cases, validation failures, permission checks.
  3. Review & approve. Tick the cases you want. Add tags (smoke, regression, custom). Reject the rest. Approved cases are saved as test cases attached to the story.
  4. Run by story or by tag. One click runs every approved case for the story. Or run every case carrying a specific tag (e.g. all smoke cases across the project).
  5. Update the story when requirements change. The platform versions stories. Test cases generated from the previous version are automatically marked stale so you know which ones to re-review.
Tip: Stories work best when the acceptance criteria are concrete. "Should validate phone format" → vague. "Phone field rejects letters; accepts +1, +44, and 10-digit US formats; shows error message in red" → the AI generates excellent cases.

Running Tests

From "go" to results in one click

Anywhere you see a saved script (Projects, Runs, Stories), there's a Run action. You'll choose how the run executes; the platform handles the rest.

Run options

Headless
Browser runs in the background. Faster, lower CPU. Use for routine runs and CI-like flows. Default.
Visible
You see the Chromium window. Useful when debugging a flaky locator or showing a stakeholder what the test actually does.
Tag include / exclude
Run only cases carrying specific tags, or skip cases carrying others. Mirrors Robot's standard --include / --exclude flags.
Parallel (Pabot)
For full suites — runs cases in multiple processes. Cuts a 30-minute regression to ~10 minutes on a 4-core machine.

What happens during a run

  • Live log streams into the page in real time — you see each step as Robot executes it.
  • Screenshots are captured automatically on failure (and on key checkpoints).
  • When the run finishes, you're sent to the Run Dashboard for that run.

The Run Dashboard

Everything you need to triage one run

Click any row in Runs (or follow the link after a fresh run completes) to land on the dashboard for that run.

What you get

  • Headline KPIs: total tests, passed, failed, skipped, total duration, pass rate.
  • Per-suite breakdown: if your run had multiple suites, see each one's pass/fail counts side by side.
  • Per-tag breakdown: useful when you ran by tag — "how did the smoke set do, how did the regression set do."
  • Test list: every test case with status (PASS / FAIL / SKIP), duration, the failure message (if any), and tags.
  • Screenshots gallery: click any screenshot to view full-size; useful for visual regression and for failure forensics.
  • Robot artefacts: direct links to log.html, report.html, and the raw output.xml — everything Robot Framework produces, viewable inline or downloadable.
  • Bundle .zip: a single archive containing log, report, screenshots, and source. Perfect for attaching to a Jira ticket or Slack thread.
Tip: If a test failed unexpectedly, open the Robot log.html from the dashboard. It shows the full keyword call tree with arguments — usually the first red keyword tells you exactly what broke.

Settings

A few knobs you'll touch occasionally

What's on the Settings page

  • LLM provider: switch between Gemini, GPT-4, Claude, Cohere, and others. Each provider needs its API key set in the environment; Settings shows you which providers are currently configured.
  • RF-MCP server: start / stop the keyword validation server (used by MCP Stepwise generation). Normally auto-managed; manual control here for debugging.
  • Keyword catalog: rebuild the catalog after you've added new custom keywords to the resource files — tells the AI about your new building blocks.

Tips for Better Results

Small habits that pay off

📝

Be specific in prompts

Name the object, name the fields, give example values. "Create a Lead Alex Wong, company Acme, state CA" beats "Make a lead" every time.

📂

One project per sandbox

Don't mix QA and UAT in the same project. Separate projects keep credentials clean and let you run a release sweep with one click each.

🎯

Tag liberally

Tag everything: smoke, regression, release-2026.1, blocker. Tags are how you'll slice runs later when "run all 800" isn't what you actually want.

🔍

Use Stepwise on new flows

For unfamiliar Salesforce screens, MCP Stepwise validates each action live — you'll catch a wrong keyword in 30 s instead of after a 4-minute failed run.

🔗

Save bundles for evidence

When closing a ticket, attach the bundle .zip rather than copy-pasting log lines. Reviewers can open the report locally and see the full picture.

🔴

Fail fast in headless

Run the smoke set headless before every PR. Switch to visible mode only when you need to see what's happening.
